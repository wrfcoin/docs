WRF Economics and WRC-20 Boundary

Current

The L1 records contribution and reward state for the implemented commit/reveal/attestation flow. That does not establish a complete token market, public economic service, or geographically fair reward system. core4#3240 tracks a known location-reference defect.

Planned

Validator stake, full slashing (only partial slashing exists today; see protocol/proof-of-publication), holder governance, WRC-20, issuance fees, sidechain/L2 fee flows, carbon credits, ESG instruments, RWA products, and marketplaces are planned. No current testnet claim should describe those target economics as active.

The investor-equity/contributor-token separation is project design intent, not legal advice or a claim of regulatory status.

  • whitepaper/05-tokenomics.md now labels target economics explicitly.
  • whitepaper/04-consensus.md identifies implemented consensus and planned

incentive behavior.

Reference Implementation Tech Stack

Current

The reference implementation is a Rust Cargo workspace whose active packages include native-chain, shared-protocol, consensus-engines, p2p, privacy components, and tools/cli. The node uses libp2p; the old minimal-TCP migration description is obsolete.

New wallets use ed25519. The settled derivation is BIP-39 mnemonic to seed with an empty passphrase, followed by the SLIP-0010 ed25519 master key with no child path. Addresses are 0x plus the first 20 bytes of SHA3-256(public key). Legacy secp256k1 addresses are receive-only. Clients, not the backend, sign.

Boundaries

Post-quantum cryptography, active L2s, and mainnet operations remain planned. The application-layer DeFi direction is read/quote-only and simulated; it is not an L1 consensus primitive and cannot move balances.

The presence of a test or workflow is not itself evidence: skipped, zero-step, or infrastructure-blocked checks do not prove a claim.

Evidence

  • whitepaper/06-tech-stack.md records these choices and boundaries.
  • The cross-client key fixture is tracked by core4#3234.
  • The checked node API description is tracked by core4#3262.

Origin Story

Overview

Wrfcoin has been through three design phases over roughly two and a half years, and the current shape only stabilized in the third. The history matters because each rejection sharpened the design — particularly the Phase 3 (Feb 2025) reboot from "ERC-20 on Ethereum" to "own L1 with domain-specific consensus and token standard." Reading the origin story explains why the current architecture is what it is rather than what an from-scratch generic-blockchain designer would produce.

Source Notes

  • [repo] 02-origin-story.md — Phase 1 (Dec 2022, "Computing Weather Forecasts"): curiosity question about running WRF on volunteer compute, building on BOINC precedent (Folding@home, Einstein@Home, climateprediction.net) and Gridcoin's cryptocurrency-rewarded BOINC participation. Working name candidates included StormCoin, ClimateCoin, EcoCoin, EarthCoin, Skyward.
  • [repo] 02-origin-story.md — Phase 2 (Jan 2023, "Skyward"): first product-shaped design. Desktop client + mobile + web dashboard + IoT registration. ERC-20 token on Ethereum. Explored: Filecoin/IPFS/Storj storage, Golem compute, Azure/AWS fallbacks, DEX integration (Uniswap/SushiSwap/PancakeSwap), atomic swaps, zk-STARK privacy, AI-enhanced forecasting.
  • [repo] 02-origin-story.md — Phase 2 introduced the investors-as-equity-holders, contributors-as-token-earners distinction. The reasoning: keeping the token tied to verifiable work (not investor sale) keeps the center of gravity in utility rather than speculation and reduces regulatory ambiguity. This distinction survives in the current design.
  • [repo] 02-origin-story.md — Phase 2's biggest weakness in hindsight: tried to be a generic blockchain platform with a weather product on top. Tokenomics, consensus, and data model were generic-blockchain-shaped, applied to weather but not optimized for it.
  • [repo] 02-origin-story.md — Phase 3 (Feb 2025, "Wrfcoin Reboot") — four key shifts:
  1. Own L1. Not a token on someone else's chain.
  2. Three-layer architecture. L1 for settlement, L2 rollups for DeFi, DAG-based sidechains for data → protocol/architecture.
  3. Climate finance as first-class concern. WRC-20 standard so third-party climate-finance, ESG, regenerative-ag, RWA tokens can sit on top → economics/wrf-token.
  4. Meta-OS concept. Wrfcoin as a coordination layer routing tasks to other DePIN networks (Render, Akash, Filecoin, Arweave, Chainlink) and rewarding results in WRF.
  • [repo] 02-origin-story.md — Timeline summary: Dec 2022 (Phase 1) → Jan 2023 (Skyward) → Feb 2025 (Reboot) → mid-2026 target (Testnet) → release/testnet-roadmap.

Design Knowledge

The phase-3 reboot's deepest lesson: a generic-blockchain on a generic L1 has no real lever to optimize for high-volume environmental data + accuracy-rewarding consensus. The constraints of ERC-20 and Ethereum's general-purpose execution model meant the most distinctive design decisions had to be implemented around the chain rather than as the chain. Making Wrfcoin its own L1 unlocked: defining PoPub, defining WRC-20, choosing DAG shape for data, separating settlement from sensor ingest. That's the entire reason the current architecture has any non-trivial shape.

The Skyward → Reboot transition also shows what gets kept: the contributor-token / investor-equity distinction, the multi-asset DePIN-ecosystem framing, and the WRF token name itself. These are the parts of Skyward that weren't ERC-20-shape-dependent.

The Meta-OS framing is the most recent shift and is also the loosest. It's compatible with the rest of the design but doesn't yet impose specific protocol-level requirements beyond cross-chain task routing.

Cross-Links

  • vision — the long-term mission this history converged toward.
  • protocol/architecture — the three-layer split the reboot produced.
  • protocol/proof-of-publication — the consensus that the reboot's "own L1" decision made possible.
  • economics/wrf-token — WRC-20 and the contributor-vs-investor split that survived from Skyward.
  • implementation/tech-stack — Rust workspace structure decided post-reboot.
  • release/testnet-roadmap — the four phases the reboot scope produced.

Open Questions

  1. Skyward (Phase 2) explored zk-STARKs, atomic swaps, AI-enhanced forecasting, and DEX integrations. Are any of these retained for post-Phase-1 work, or fully discarded?
  2. Meta-OS framing ("Wrfcoin orchestrates environmental analysis across the broader DePIN ecosystem") is the most under-specified piece of the current design. What concrete protocol-level support does it require beyond cross-chain task routing? Is there a wrapping standard (wRNDR, wFIL, wLINK, wAKT, wTAO) spec?
  3. Investor-equity / contributor-token distinction is project convention. Is there a written governance or legal document codifying it, or does it live only in the whitepaper text?
  4. The two-and-a-half year history is single-developer pace. Is the current testnet target (mid-2026) revised against actual single-developer velocity, or is it inherited from the Phase 3 reboot announcement?
  5. Phase 1 → Phase 2 transition was Dec 2022 → Jan 2023 (one month). Phase 2 → Phase 3 was Jan 2023 → Feb 2025 (~25 months). The asymmetry is presented as "intermittent work" — what specifically broke the inertia in Feb 2025?

Architecture and Implementation Boundary

Current

Wrfcoin currently has one Proof-of-Publication L1. Its implemented environmental-data flow is commit, reveal, oracle attestation, quorum decision, and deterministic reward state. The Actix launch_api route registration is the source of truth for the node HTTP surface.

The repository can be ahead of the private deployment. “Implemented” therefore does not mean “publicly reachable”; use release/testnet-roadmap and the root STATUS.md for that boundary.

Planned

L2 rollups, a DAG data sidechain, full stake slashing (only partial slashing exists today), carbon/RWA markets, and cross-layer accountability are planned. They are not active testnet layers or guarantees. The old three-layer diagram describes target architecture only.

Implementation map

Relevant Rust workspace packages include native-chain, shared-protocol, consensus-engines, p2p, privacy tooling, and tools/cli. A crate's presence does not prove it is selected or healthy in a deployed node.

Proof of Publication (PoPub)

Implemented core

PoPub is the active native-chain consensus path. Contributors commit and reveal observations; oracle attesters submit signed votes; a configured quorum decides acceptance; and the L1 records contribution and reward state. The current private testnet registers three attesters with a quorum of two, but only two run online; losing either online attester stops contributions from finalizing even while blocks continue.

Partial economics

Reward and attestation machinery exists, but the broader four-role market is not complete. Forecasting and verifier economics are partial, and core4#3240 tracks a known location-reference defect affecting reward fairness.

Planned

Slashing is partial. On core4 main, three consecutive low-quality reveals that reached quorum cost a contributor 15 base units (0.00000015 WRF), and validators can be slashed for equivocation. A reveal-time out-of-range slash exists but has no effect (core4#3214, private). Slashing station owners for bad data was ruled in by the owner on 2026-09-21 and is still being designed (core4#3218, private).

Variable-specific confidence thresholds, anti-collusion policy, forecaster reputation curves, and cross-layer accountability remain planned.

  • whitepaper/04-consensus.md records the implementation boundary.
  • core4/native-chain/src/bin/launch_api/routes/oracle.rs serves oracle routes.
  • core4#3240 records the unresolved reward-fairness defect.

Cross-Section Design Tradeoffs

This page records design questions, not current capabilities.

Current pressure points

  • Availability versus quorum: the private testnet registers three attesters

with a quorum of two, but only two run online, so losing either online attester stops real reveals from finalizing while the chain still advances.

  • Reward activity versus fairness: reward state exists, but a known

location-reference defect prevents a geographically production-ready claim.

  • Repository versus deployment: code on main can be newer than pinned

private images; source presence is not public reachability.

  • Public documentation versus release: documentation may be prepared before

deployment, secret scanning, and human visibility decisions are complete.

Planned-design tensions

  • L2 throughput versus the added proving/challenge trust model.
  • DAG-sidechain autonomy versus L1 accountability and rollback limits.
  • Rich WRC-20 environmental semantics versus implementer simplicity.
  • Slashing strength versus calibrated evidence and false-positive risk.
  • Broader DeFi utility versus the accepted read/quote-only simulated boundary.

None of these planned designs should be inferred from the implemented L1.

active1 sources5 open Qupdated 2026-05-18

Vision

Overview

Wrfcoin's stated purpose is to build a decentralized, hyperlocal, community-governed augmentation layer for environmental data and compute — explicitly additive to (not a replacement for) NOAA / ECMWF / NWS / equivalent institutional forecasting. The mission is positioned as a public-good problem solved by decentralized incentives: anyone can contribute data, anyone can contribute compute, anyone can build climate or environmental applications on top, and the protocol makes it costly to be wrong and rewarding to be right.

The vision rests on three pre-conditions the whitepaper claims have only recently become true: cheap sensors, distributed compute (BOINC → Render / Akash / Bittensor), and mature cryptographic coordination. The combination supports a long-tail data commons that institutional forecasting can't economically build.

Source Notes

  • [repo] 01-vision.md — Three brittle assumptions the chapter names in current forecasting: (1) data flows from a small number of sources, (2) compute lives in a few supercomputers behind institutional walls, (3) the public is expected to trust the result on institutional reputation alone.
  • [repo] 01-vision.md — Three changes that opened the design space: cheap commodity sensors, decentralized compute precedent (BOINC, Render, Akash, Bittensor), and mature cryptographic coordination via blockchains.
  • [repo] 01-vision.md — Wrfcoin is explicitly not: (a) a speculation vehicle, (b) anti-institutional, (c) a single-app blockchain.

Design Knowledge

The vision chapter functions as a constraint generator for the rest of the whitepaper. Every later choice has to satisfy: additive to institutional forecasting (not replacement), pays contributors fairly, makes lying expensive, supports a third-party ecosystem of climate apps. The "infrastructure layer for environmental data" framing is what justifies separating L1 from data sidechains: a pure-finance L1 wouldn't need DAG-shaped sensor ingest, and a pure-data network wouldn't need WRF as a stake-and-slash asset.

The deliberate distance from speculation framing (no investor token sales, no DeFi-first design) is a strategic choice, not a technical one — it shapes the regulatory posture, the contributor incentive structure, and which kinds of users the network optimizes for. The same protocol designed with a speculation-first posture would likely look quite different at the parameter and standard-library level.
